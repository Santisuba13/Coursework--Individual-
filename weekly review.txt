WEEK 2- Analysis and Specify Software Quality Requirements 
- For this task, Ive selected the FUnctional requirement "FR-SL-1: Management of Society" where I will be discussing its quality requirements.
  -Security and Privacy protection: 
Requirements
The system must only allow authenticated society leaders to access event creation and update features or information
A leader can only edit events belonging to their own society. No other user type should be able to change these records.
All event data stored on the cloud must use encrypted storage. This applies to text fields, photos, videos and external links 
All communications between the app and cloud microservices must be encrypted to prevent unauthorised access or interception.
The system must validate the leader’s session before accepting any update. If the session expires, the action must be blocked 
Uploaded promotion materials must go through safe file handling checks to prevent harmful files from being stored
The system must restrict visibility based on event scope.internal society events must not expose organiser details to non members.

  -Peformance:
The event creation and update processes must feel fast and simple. Society leaders should not wait long when submitting information or uploading materials

Requirements
The event creation form should load quickly, even when the leader has weak or unstable mobile data
When uploading photos or videos, the system should compress files and upload them in the background so the app stays responsive
Submitting an event should take only a few seconds under normal system load
When event updates are pushed across the federation, these background actions must not slow down the leader’s experience. Notifications to students and unions should be handled asynchronously.
When confirming the creation of an event or update, the process of it should be almost immediate
When updating an event, the system should only process that field that changed, that way, it will reduce processing time 

  -Reliability:

Event creation and editing must always work in a predictable way. A society leader cannot risk losing event data or publishing incomplete information.

To mitigate these risks, we need to ensure:
If the leader loses connection during submission, the system must store the event safely or retry the action when the connection returns.
If an upload fails halfway through, the system must not corrupt the event. The leader should receive a clear message asking them to retry without losing the rest of the form 
Event records stored in the cloud must remain consistent. Each update should fully apply or not apply at all
The system should maintain an internal version record so updates can be traced if needed by union or USU officers
This system ensures that event data isn't lost or corrupted.

  -Scalability:

As many societies from different universities will be using this feature/system at the same time, we need to ensure that the system handles this without failing or slowing down

Requirements
The microservices that support event creation and updates must handle thousands of requests during busy periods.
The cloud storage must scale to support a large number of uploaded photos and videos from many societies.
WHen an event is created with a nationwide promotion scope, the system may need to notify thousands of students. This process must not block the leader’s ability to use the app.
The database must handle long term storage of event records across multiple years without affecting search or update speed.
